前端重设计：量化交易工作台

围绕三个日常动作重构信息架构：定明天怎么交易、训练和验证模型、研发因子。 一切以磁盘上的产物契约为数据源，重计算走会话子进程，前端只做呈现与调度。

Dash + dbc 延续 step-report 自描述契约 版本 v2.0 · 2026-10 配套 daily_run.sh / predict_tomorrow.py

0设计目标

把「一个能跑研究的仪表盘」升级为「一个能支撑每日实盘决策的工作台」。

需求现状问题设计应答
① 制定次日仓位与交易策略 订单 CSV、持仓、风控状态散落在 outputs/，无统一视图；nextday 会话产物与 CLI 产物两处割裂 交易台作为首页：订单执行单 + 目标仓位 + 风控状态灯 + 账户净值 + 偏差告警，一屏看完今晚要做什么
② 训练新模型并回测 会话列表平铺四种模式，champion/staging 门控状态不可见；回测结果与模型身份无关联 模型实验室：任务列表按「模型身份」组织，champion/staging 卡片置顶，回测结果挂在产生它的配方指纹下
③ 因子研发并回测，看清每个因子的特征和贡献 Factor Lab 只有两张静态 CSV 图；因子定义（YAML）与评估结果分离；无单因子下钻；无「因子在模型里的贡献」视角 因子工作台：因子库总览 → 单因子详情（定义/IC 衰减/分层/换手/相关簇/模型内贡献）→ 公式编辑器 → 一键评估回测的完整闭环
一以贯之的量化直觉：这个系统的实证结论是「选股 alpha 温和（年化 ~+15%，NW-t<2）、风控层贡献 Sharpe +0.98、边际集中在排序头部」。 因此前端的第一公民不是「收益曲线多漂亮」，而是信号健康度（IC 衰减、窗口占比、头部超额）与风控状态（暴露、回撤刹车、IC 降仓）—— 把它们放在每个页面最显眼的位置，防止使用者被单条净值曲线误导。

1设计原则

  • 产物契约驱动：前端只读 outputs/、data_cache/、models/、factor_library/ 的 JSON/parquet/YAML 契约，不在请求路径上做计算。所有重活（训练/回测/评估）封装为会话子进程，落盘自描述 step report。
  • CLI ≡ 前端：CLI 跑出的 canonical 产物（outputs/walkforward/、orders_*.csv）前端原样展示；前端发起的会话与 CLI 产物同构同路径。同一份结果，两个入口。
  • 先问「信不信」，再问「赚没赚」：每个汇总指标旁边必须有它的可信度上下文——窗口数为正占比、NW-t、OOS 长度、种子离散度。
  • 泄露防线可视化：因子评估一律标注「仅用训练段」；任何展示未来函数嫌疑的数据（如未成熟 IC）用醒目的「未成熟」水印标识。
  • 空态即教程：产物不存在时（如实盘未跑过），页面显示「如何生成它」的一条命令，而非空白或报错。

3.3 风控状态灯的细节（本系统的实证核心）

五层各渲染一个灯：🟢 未触发 / 🟡 部分降仓 / 🔴 强约束，旁边直接标注当前乘数与原因，例如：

vol目标   🟡 ×0.62   20日实现波动 24% > 目标 15%
回撤刹车  🟢 ×1.00   当前回撤 -3.1%（阈值 -20%）
IC 降仓   🔴 ×0.20   近20日 OOS IC = -0.031 衰入负区
IV 降仓   🟢 ×1.00   opt_vix_like 处于中三分位
为什么放这么显眼：对照实验（outputs/ablations/walkforward_riskoff）证明风控全关时 Sharpe 从 +2.48 掉到 +1.50、回撤翻倍。 交易台必须让使用者一眼看到「今晚的风控乘数」，这是小本金账户最重要的数字。

4页面二 · 模型实验室（/models）

需求②：训练新模型并回测。设计取向——以「模型身份」为主线，回测是模型的验证记录，不是孤立任务。

4.1 布局线框

A. Champion 卡片：model_id · 配方摘要 · 最近评估 Sharpe/MaxDD · 「上次验证」时间
B. Staging 候选列表：各候选 vs champion 的双回放对比结论（晋升/留档/拒绝 + 原因）
C. 验证历史时间线：每次 walkforward / backtest / robustness 会话的 Sharpe 点图
（同一配方指纹的点连成线 → 看出同一模型的衰减）
D. 「新建任务」面板：
walkforward / backtest / robustness / nextday 四模式参数表单
E. Runs 任务表：状态徽章 · 进度 · 耗时 · 产物链接 · 删除
（吸收原会话列表，加 CLI 产物行：canonical walkforward 作为特殊 run 置顶）

4.2 Champion / Staging 卡片（门控可视化）

字段来源说明
model_id / created_atmodels/champion/manifest.json日期+12位配方指纹
配方摘要manifest.config_snapshotfeat_cols 数 / fw / ensemble_models / train_window 等，可展开全量 JSON
最近评估staging/<id>/evaluation.json（晋升时归档）+ tracking双回放 Sharpe、回撤差
模型年龄manifest.created_at vs 交易日历超 MAX_MODEL_AGE_DAYS 亮黄灯（自适应重训的硬上限）

Staging 卡片额外提供两个操作：人工晋升（调 predict_tomorrow.py --promote <id> 等价接口）与拒绝归档。每次操作写审计记录。

4.3 验证历史时间线（防自欺的关键组件）

把每次验证会话的 (generated_at, Sharpe) 打点，按 配方指纹 分组连线。用途：

  • 同一配方 Sharpe 逐次下滑 = 信号衰减的直观证据（比单次数字更有说服力）；
  • ±0.4 的同配置随机波动带用半透明色带标出，防止把噪声当改进；
  • 每个点可点击 → 跳 /runs/<id> 看完整 step report。

4.4 新建任务面板

复用 pipeline/registry.py::PARAM_SCHEMA 动态渲染（现状能力保留），但加两处强化：

  • 成本预告：每个模式标注预期耗时（walkforward 全市场 ≈ 5h / robustness 3 seeds ≈ 15h / nextday ≈ 分钟级）与 CPU 占用，防止误触长任务；
  • 参数diff预览：提交前显示「本次参数 vs 当前 champion 配方」的差异清单，让实验意图显式化。
门禁指标前置：walkforward 完成后，报告头部固定渲染三枚「可信度徽章」——正 Sharpe 窗口占比（<60% 亮红）、PredIC 为正占比（<50% 亮红）、NW-t（<2.0 亮黄）。 规则与 CLI 的 meta.json 新字段 sharpe_pos_ratio / predic_pos_ratio 完全一致。

5页面三 · 因子工作台（/factors）

需求③：因子研发 + 回测，且「清晰看到每个因子的特征和贡献」。这是三页中信息密度最高的，分三级：库总览 → 单因子详情 → 研发编辑器。

5.1 因子库总览（/factors）

A. 筛选条：类别（动量/反转/量价/价值/北向/公式库）· 准入状态 · 启用状态 · 搜索
B. 「运行全量评估」按钮（→ eval 会话，产出 factor_eval.csv）
C. 因子主表（见下）
D. 冗余簇热图（diag_factor_corr.csv，|corr|≥0.8 聚簇标框）
E. 模型 vs 最强单因子（diag_model_vs_factor.csv）：模型是否真有增量

主表每行一个因子，列设计直接对应「特征与贡献」：

列内容来源
因子id + 中文名 + 类别徽章factor_library/*.yaml / 原生族注册表
RankIC / ICIR评估期均值，ICIR 着色（绿 >0.3 / 红 <0）outputs/factor_eval.csv
IC_t / 准入t 统计量 + 通过/未通过徽章（GATE_IC_T=2.0 等）同上
多空收益 / 单调性5 层分层 Top-Bottom、层间单调性比例同上
换手率top 组日换手（成本敏感度的直接代理）同上
近期衰减逐窗口 RankIC 迷你 sparkline（w0..wN）outputs/diag_factor_ic_decay.csv
模型内贡献champion 集成中的滚动 IC 权重 / GBM 重要性分位models/champion/manifest.json + ensemble state
冗余|corr|≥0.8 的簇标签（如「与 turnover_rate 同簇」）diag_factor_corr.csv

5.2 单因子详情（/factors/<id>）——「特征 × 贡献」的完整答卷

头部：因子名 · 类别 · 公式（DSL 源码语法高亮）· expected_sign · 版本/作者
操作：「重评估此因子」「加入/移出 LINEAR_FACTORS 建议」
P1. IC 衰减曲线：逐窗口 RankIC 柱状 + 滚动 IC 线
回答：它还活着吗？
P2. 5 层分层净值曲线
回答：单调吗？头部还是尾部赚钱？
P3. IC 分布直方图 + 正 IC 占比
回答：稳定还是靠少数几天？
P4. 相关邻域：与 Top10 最相关因子的横向条形
回答：它是独立信息还是重复？
P5. 模型内贡献面板：① ic_linear 腿中的滚动 IC 权重时序 ② GBM 腿重要性 ③ 该因子在/不在特征集的两次 walkforward 对比入口
回答：模型真的在用它吗？去掉会怎样？
P6. 覆盖面与缺失率：按日的非 NaN 占比
回答：它覆盖全市场还是只有大盘？
「贡献」的三层定义（每层层层递进）： ① 独立预测力：RankIC / ICIR / IC_t（factor_eval 框架，训练段内评估防泄露）； ② 边际贡献：与现有因子库的相关性（冗余簇）、模型 vs 最强单因子差； ③ 组合内贡献：champion 集成中的实际权重 / 重要性，以及留一法（leave-one-out）walkforward 对比。 三层分开呈现——一个 IC 很高但与动量簇冗余的因子，真实贡献是零，表格必须让这一点无处遁形。

5.3 公式因子编辑器（/factors/new）——研发闭环

左：YAML/DSL 编辑器（id/formula/tags/expected_sign，带 schema 即时校验 + 依赖解析预览）
右：实时预览：公式解析树 → 涉及的原始列 → 与现有因子的相关性预检
底部操作条：「保存到 custom.yaml 草稿」→「发起评估会话」（USE_FORMULA_FACTORS=1 + FORMULA_FACTOR_SUBSET=<id> 的 backtest/walkforward）→ 结果回填因子详情页

流程即 factor_library 的可视化封装：写公式 → 静态校验（schema.py 的字段 + explicit_deps）→ 评估会话 → 看三层贡献 → 一键 enabled=true 入库。评估会话通过 param_env 注入 USE_FORMULA_FACTORS=1，与 CLI 完全同构。

6页面四 · 行情观察（/market）

保留现有实现（个股 K 线 + 指标叠加、市场宽度、等权指数），仅做两处补强：

  • 与交易台联动：从订单执行单/持仓表点 symbol 直接跳 /market?symbol=xxx 并高亮买卖点参考价（limit_price）；
  • 信号上下文：个股视图叠加「当前模型排名分位 + 所属因子的暴露」，回答「模型为什么选它」。

7横切 · 会话引擎与 step-report 契约

现有机制是本系统最该保留的资产，新前端继续站在它上面：

  • 自描述 step report（pipeline/context.py）：{step,title,status,elapsed,summary,kpis,tables,figures,notes}，通用渲染器零成本承接新步骤——因子评估、留一法对比等新能力只需写 pipeline step，不需写前端。
  • 调度独立化（必要改造）：把 webapp/sessions.py::tick() 的进程内心跳 + 内存 Popen 表抽成独立调度模块（pipeline/scheduler.py），webapp 与未来的 CLI/TUI 共用；状态全部落盘（session.json），webapp 重启不丢任务。
  • 进度契约：沿用 current_progress（phase/pct/eta/extras）；walkforward 已有逐窗口 ETA 日志，把窗口号/Sharpe 也桥进 extras，前端渲染迷你窗口时间线。
  • 并发与资源护栏：全市场任务内存峰值 ~8-10GB，并发上限默认 1 保持；提交长任务前弹「预计 5h / 峰值内存」确认。

9技术方案与迁移计划

9.1 技术选型：延续 Dash，重构信息架构

不更换框架。理由：① step-report 契约已让渲染层与计算解耦，痛点在信息架构而非技术栈；② 现有 dataio 的 lru_cache + 预热机制对 6M 行面板已验证；③ 团队（当前维护者）已熟悉 Dash 回调模式。升级点：引入 dash-ag-grid 承载因子主表与订单执行单（排序/筛选/行内操作远比 html.Table 顺手），图表继续用 Plotly。

9.2 分阶段实施

阶段内容验收
P0 骨架新路由与侧边栏；调度器独立化；交易台只读版（订单/持仓/风控灯/账户快照）daily_run.sh 一晚产物在首页完整可读
P1 模型实验室champion/staging 卡片、验证时间线、Runs 表迁移、新建任务面板（成本预告+参数diff）从前端发起 walkforward → 结果与 CLI canonical 同构展示
P2 因子工作台因子主表（含模型内贡献列）、单因子详情六面板、冗余簇热图任一因子三层贡献一屏可答
P3 研发闭环公式编辑器 + 评估会话 + 入库流转；留一法对比入口；行情页联动新公式因子从撰写到入库全程无 CLI

9.3 兼容与清理

  • 旧路由 /session/<id> 301 到 /runs/<id>；旧会话产物原样可读。
  • canonical 产物路径不变（outputs/walkforward/ 等），CLI 用户无感知。
  • 删除遗留散文件产物（outputs/walkforward_oos_*.html 等）在迁移收尾时统一归档。

10非目标

  • 不做券商直连/自动下单：执行环节保持人工（订单 CSV + 勾选确认），本系统定位是决策支持；
  • 不做多账户/多用户/权限体系：单机单用户研究工作站；
  • 不做实时行情推送：日频系统，分钟级刷新无意义，轮询间隔 ≥2s 足够；
  • 不在前端引入训练计算：一切重活走会话子进程，前端进程保持可热重载、可随意重启。
